# Дизайн: автономный сервер на ThinkPad T420 («konotop»)

Дата: 2026-08-30
Статус: черновик на ревью

## 1. Обзор и цели

Ноутбук ThinkPad T420 превращается в тихий, самовосстанавливающийся домашний
сервер, который стоит у родителей (нетехнических пользователей) и управляется
удалённо. Требования:

- Автоматически включаться при подаче питания (частые отключения света).
- Полностью удалённое администрирование в любой момент.
- Родители могут восстановить систему «одной кнопкой» при поломке, без навыков.
- Минимальное потребление и шум в простое.
- Docker как платформа для сервисов.
- Сервисы: торрент-клиент, скачивание готовых файлов, SMS→Telegram (+звонки как
  спайк), exit-прокси «весь браузер через дом», веб-панель.

### Железо
- ThinkPad T420, 8 ГБ RAM.
- SSD 240 ГБ — ОС, конфигурация, Docker.
- HDD 1 ТБ — данные (торренты, файлы). Восстановление его не касается.
- Модем **Sierra Wireless MC7304** (LTE) с SIM — используется для SMS/сервиса
  симки, **не** как интернет-канал.
- Интернет у родителей — домашний Wi-Fi/Ethernet (основной канал).

### Ключевые решения (зафиксированы)
- **ОС:** Debian stable.
- **Восстановление:** снимок раздела через partclone на отдельном разделе SSD,
  запуск из GRUB. НЕ иммутабельная ОС, НЕ btrfs-снапшоты.
- **Overlay-сеть:** Tailscale.
- **Публикация веб-морды наружу:** Cloudflare Tunnel + Access (бесплатно).

## 2. Диски и разметка

### HDD 1 ТБ — данные
- Одна ФС (ext4), монтируется в `/srv/data`.
- Bind-mount в контейнеры (загрузки, файлы, медиатека).
- **Восстановление никогда не трогает этот диск.**
- Спиндаун в простое (`hdparm -S` / `hd-idle`) — раскручивается только при
  торрент-активности. Это основной вклад в тишину/нагрев.

### SSD 240 ГБ — система
| Раздел | Назначение | Размер |
|--------|-----------|--------|
| p1 | ESP (загрузчик) | ~1 ГБ |
| p2 | root: ОС + конфиг + Docker (образы и volume'ы) | остаток (~170 ГБ) |
| p3 | «золотой снимок» раздела p2 + recovery-среда | ~50 ГБ |
| p4 | персистентная зона (секреты, вне восстановления) | ~2 ГБ |

Сумма укладывается в ~223 ГиБ полезной ёмкости SSD 240 ГБ. Снимки на p3
хранят только занятые блоки (~10–30 ГБ каждый), поэтому 50 ГБ хватает на две
версии (старую и новую при re-bless).

## 3. Базовая настройка ОС

### Автозапуск при питании (юзкейс 1)
Настройка BIOS T420: `Config → Power → After Power Loss = Power On`. Программно
не решается. Пункт чеклиста при первичной настройке.

### Тишина и потребление в простое (юзкейс 4)
Определяется НЕ дистрибутивом, а настройками питания:
- `TLP` (родной для ThinkPad) — управление питанием.
- CPU governor `powersave`/`ondemand` под нагрузку.
- Спиндаун HDD в простое.
- Минимум фоновых демонов (netinst-инсталляция без DE и лишних служб).

### Удалённый администраторский доступ (юзкейс 2)
- `SSH` как канал управления, доступ по ключам, пароль отключён.
- SSH слушает **только на интерфейсе Tailscale** (не торчит в LAN/интернет).
- Достижимость снаружи (в т.ч. за CGNAT) обеспечивает Tailscale (см. §5).

## 4. Восстановление (юзкейс 3)

### Модель
На p3 хранится **снимок раздела p2** в золотом состоянии (только занятые
блоки — через partclone/fsarchiver, как Clonezilla). Восстановление и повторная
фиксация выполняются из отдельной recovery-среды.

### Меню GRUB
- **Обычная загрузка** — грузит p2.
- **Восстановить** — грузит recovery-среду с p3; она пере-форматирует p2 и
  распаковывает в него золотой снимок; перезагрузка. p3, p4 и HDD не трогаются.

Пункты крупные и понятные, выбор стрелками — рассчитано на родителей.

### Повторная фиксация золотого снимка (re-bless), редко, удалённо
1. Правлю сервисы на живом p2, обкатываю.
2. Командой ставлю одноразовую загрузку в recovery (`grub-reboot`) и перезагружаю.
3. Recovery снимает p2 (неактивный, консистентный) в **новый** файл на p3.
4. Новый снимок проверяется, и лишь затем заменяет старый.
5. Система сама возвращается в обычную загрузку.

Старый снимок хранится до подтверждения нового → всегда есть валидная точка
отката. Под две версии снимка заложен p3 ~50 ГБ (см. §2).

### Персистентная зона (p4)
Секреты, которые обязаны пережить восстановление, лежат на p4 и подхватываются
при старте. Иначе «Восстановить» сбросил бы их и **отрезал удалённый доступ**.
Содержимое p4:
- Ключ ноды Tailscale.
- Ключи/креды exit-прокси (см. §8).
- Токен Cloudflare Tunnel.
- Токен Telegram-бота, креды сервисов.

Recovery-среда **никогда** не форматирует p4.

## 5. Сеть и удалённый доступ

### Tailscale — единая приватная сеть
Одна overlay-сеть закрывает три юзкейса: удалённый админ (2), exit-прокси на
личных устройствах (8), доступ к веб-морде со своих устройств (9).
- Пробивает NAT/CGNAT через DERP-релеи (бесплатно).
- Трафик E2E-шифрован (WireGuard); координатор видит только метаданные.
- Ключ ноды — на p4 (переживает восстановление).
- **Важно:** установка Tailscale сама по себе НЕ перенаправляет трафик; exit-node
  — отдельный явный тумблер.

### Cloudflare Tunnel + Access — публикация веб-морды (для юзкейса 9)
Для доступа к веб-морде с **чужого** браузера без установки клиента:
- `cloudflared` на боксе делает исходящий туннель (работает за CGNAT).
- Публичный `https://<адрес>` ведёт на веб-морду.
- Защита — Cloudflare Access (бесплатно, вход по email-коду).
- Токен туннеля — на p4.

### Развилка CGNAT (влияет на §8)
Неизвестно, за CGNAT ли дом. **Проверка (сделать на месте):**
1. На устройстве в домашней сети: `curl ifconfig.me` — публичный IP.
2. В админке роутера — его WAN-IP.
3. Совпадают и не из `100.64.0.0/10` → CGNAT нет. Иначе → CGNAT есть.

## 6. Сервисы (Docker)

Всё в Docker + docker-compose. Reverse-proxy **Caddy** даёт чистые адреса и TLS
для всех веб-морд, а также точку для публикации через Cloudflare Tunnel.

| Сервис | Тула | Юзкейс |
|--------|------|--------|
| Торрент-клиент | qBittorrent (веб-морда) | 6а |
| Файловый доступ | filebrowser (скачивание с HDD по HTTPS) | 6б |
| Дашборд | Homepage (статус контейнеров, ссылки, место на диске) | 9 |
| Reverse-proxy | Caddy (авто-TLS) | инфра |

Данные торрентов и файлов — на HDD (`/srv/data`), bind-mount в контейнеры.

## 7. SMS → Telegram и звонки (юзкейс 7)

### SMS → Telegram (обязательная часть)
- Модем MC7304 через `ModemManager`/`mmcli` (или `gammu-smsd`).
- Небольшой собственный сервис-мост: читает входящие SMS, шлёт в Telegram-бота
  (Telegram Bot API). Гибче готовых тяжёлых пакетов.
- Токен бота — на p4.

### Звонки — СПАЙК (не обязательная часть)
MC7304 — LTE-модуль; голосовой канал через AT-команды часто недоступен.
**Задача спайка:** выяснить, поддерживает ли конкретный MC7304 голос (профиль
`AT+CLCC`/voice, наличие voice-capable прошивки/USB-audio). По результату решить,
реализуемы ли звонки или нужен отдельный VoLTE-гейтвей / другой модем. Код спайка
— throwaway, в золотой образ не входит до принятия решения.

## 8. Exit-прокси «весь браузер через дом» (юзкейс 8)

Цель: весь веб-сёрфинг выходит в интернет через домашний канал родителей (сайты
видят домашний IP). Разные пути для разных устройств.

### Личные устройства (телефон, домашний ноут)
- Tailscale + маленький **SOCKS5-прокси** на боксе, привязанный **только к
  интерфейсу Tailscale** (снаружи не виден).
- В браузере — расширение-переключатель прокси (Proxy SwitchyOmega), указывает на
  `socks5://<tailnet-ip>:1080`.
- Бесплатно, за CGNAT работает, свой Chrome-экстеншн писать не нужно.

### Рабочий ноут (нельзя ставить клиент)
Только Chrome-расширение, без системного клиента. Итоговый путь зависит от CGNAT
(проверка — §5). **В спеке заложены оба случая:**

- **Случай 1 — дом НЕ за CGNAT:** форвард-прокси с аутентификацией на боксе,
  порт 443. Расширение указывает на `дом:443`. Без VPS, без клиента.
- **Случай 2 — дом за CGNAT:** нужен публичный релей. Бесплатный вариант —
  бесплатный облачный VM (напр. Oracle Cloud Always Free) с публичным IP: бокс
  делает исходящий туннель к VM, рабочий ноут ходит на VM, трафик выходит через
  бокс (домашний IP). Минус — обслуживание ещё одной машины.

Решение между случаями принимается **после проверки CGNAT**.

### Безопасность прокси
Любой торчащий в интернет форвард-прокси (Случай 1 и релей в Случае 2):
обязательная аутентификация (логин/пароль или mTLS), желательно ограничение по
IP. Иначе — открытый прокси, который найдут и начнут абьюзить.

### Оговорка
Рабочий ноут часто под MDM/политиками работодателя; расширения могут быть
запрещены, а заворачивание трафика — нарушать политику. Ответственность на
пользователе.

## 9. Безопасность (сводно)

- SSH — только по ключам, только на интерфейсе Tailscale.
- Внутренние веб-морды — не торчат в интернет; доступ через Tailscale.
- Наружу через Cloudflare Tunnel публикуется только веб-морда, за Cloudflare
  Access.
- Форвард-прокси — с аутентификацией (§8).
- Секреты — на p4, не в золотом образе и не в git.
- `unattended-upgrades` для security-патчей Debian.

## 10. Конфиг как код и воспроизводимость

Всё состояние системы описано декларативно, чтобы золотой снимок был
воспроизводим, а не «магией, накрученной руками»:
- `docker-compose` файлы для всех сервисов.
- Скрипты провижининга (bash/Ansible) для системных настроек (TLP, разметка, SSH,
  GRUB-пункты, монтирование, спиндаун).
- Секреты подключаются из p4, в репозиторий не коммитятся.
- Репозиторий проекта — источник правды; re-bless фиксирует уже описанное
  состояние.

1. BIOS: автозапуск при питании, порядок загрузки.
2. Разметка SSD (p1–p4), ФС; HDD → `/srv/data`.
3. Установка Debian stable (netinst, минимум).
4. Базовая настройка: SSH (ключи), TLP, governor, спиндаун HDD,
   `unattended-upgrades`.
5. Tailscale (ключ ноды → p4), SSH на интерфейс Tailscale.
6. Docker + docker-compose; Caddy.
7. Сервисы: qBittorrent, filebrowser, Homepage (данные → HDD).
8. SMS→Telegram мост; спайк по звонкам.
9. Cloudflare Tunnel + Access для веб-морды (токен → p4).
10. Проверка CGNAT → реализация §8 по случаю.
11. Настройка recovery-среды на p3, пункты GRUB, скрипты restore/re-bless.
12. Снятие первого золотого снимка p2 → p3.
13. Тест: «Восстановить» из GRUB, проверка сохранности p4 и HDD.
